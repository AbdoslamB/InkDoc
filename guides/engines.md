# Engines and add-ons

The downloadable parts of InkDoc: the Docling engine pack, add-ons (models), and GLM-OCR with
its `llama-server` runtime, plus the download code they share. Whether something should be a
download at all is decided by AGENTS.md's "Core or add-on". The files this guide covers are
listed in AGENTS.md's routing table.

## Rules

- Every downloaded file is pinned by SHA-256 and checked before use. A download from a mirror
  must match the same pin as upstream.
- Downloadable add-ons may only ever be data (models, fonts, dictionaries) through the signed
  `AddonManager` catalogue, never code that runs in the page.
- Catalogues are generated by their scripts, never edited by hand: `glm_ocr_catalogue.json` by
  `scripts/build_glm_ocr_catalogue.py`; the layout model's entry by
  `scripts/build_layout_addon.py`.
- When `manifest.json` moves to a new Docling pack, add the outgoing pack to
  `engine_manifest.EARLIER_PACKS`, so installed packs keep working.
- Status checks never hash files and never touch the network. They read the completion marker
  (GLM-OCR) or the recorded sizes (add-on pack copies).
- Engine processes are contained: they can't outlive InkDoc.

## How it works

### Shared download code

`download_utils.py` holds the shared download and archive code: HTTPS only, with an explicit
host allowlist; every redirect hop validated; Range resume; a disk-space check before the
download; a maximum size; safe extraction (path traversal, zip/tar bombs, symlinks, file
modes).

### The Docling engine pack

`engine_manager.py` / `manifest.json` is the Docling engine pack (built by `build-packs.yml` on
a `docling-pack-vN` tag from `scripts/docling-constraints.txt`; `manifest.json` is that
release's merged manifest, copied in unchanged). `engine_manifest.py` decides which platforms
are supported: those with a verified entry in the bundled manifest.

- **One pack per release.** Each release names one pack. An earlier pack that is installed
  keeps working: it is checked against its own interpreter and worker hashes in
  `engine_manifest.EARLIER_PACKS` (add the outgoing pack there whenever `manifest.json` moves
  on), and `/engines` reports `update_available` until the user updates from the card.
- **Updating.** The update downloads and verifies first, then waits for a running Docling
  conversion and stops the worker (`DoclingWorkerClient.paused()`). It moves the add-ons
  installed inside the old pack into the new one (`AddonManager.carry_over`), has the new
  worker load them (`reconfirm`), and keeps the installed pack if anything fails.
- **The worker.** `engines/docling_worker_client.py` starts the pack's own Python in isolated
  mode (`-I`), checks the pack's integrity at launch, runs one conversion at a time, stops it
  when idle, and talks to `engines/worker.py` through files, with stdout redirected at the C
  level so library output can't corrupt the protocol. `engines/docling_engine.py` is the
  adapter.
- **Code languages.** `engines/code_language.py` puts the programming language Docling's code
  enrichment detected back on the Markdown code fences, which Docling's Markdown serializer
  drops.

### Add-ons

`addon_manager.py` / `addons.json` are the downloadable add-ons.

- **Targets.** `target` "docling_pack" installs into the Docling pack's models folder (the
  code/formula model, confirmed by the pack worker); "inkdoc" installs into InkDoc's own
  `addons/` folder beside `engines/` (the layout model).
- **Pack copies.** An "inkdoc" add-on may name a `pack_copy`, the same files inside the Docling
  pack pinned by SHA-256 (and size, so the status path spots another model without hashing):
  it is then usable without a download (`provided_by_pack`), and `model_location()` returns
  InkDoc's own install first, but only while the catalogue pins its files, else that copy.
- **One shape.** Status, install, verify and remove share one shape for both targets; verify
  fails when there is nothing to check.
- **Validation.** `validate_addon_entry` checks `target`, `model_dir` and `pack_copy` in every
  state, and a published "inkdoc" entry must pin the pack copy's files with the same digests.
- **Building.** `scripts/build_layout_addon.py` builds the layout model's archive
  (reproducible) and catalogue entry from the pinned Hugging Face revision or a local copy, and
  refuses any model but the pinned one. `scripts/build_addon.py` builds the Docling pack's
  add-ons.

The code that runs the layout model is in [tables.md](tables.md).

### GLM-OCR

- **Catalogue.** `glm_ocr_catalogue.py` / `glm_ocr_catalogue.json` hold the GLM-OCR pins:
  model files (Hugging Face) and llama.cpp runtime builds per platform, each with sha256 and
  ordered sources (upstream first, InkDoc mirror second). `validate_glm_catalogue`
  (UNRELEASED / PUBLISHED / DEFECTIVE) is the one validator used by the app, CI and the signer.
  A signed remote catalogue (same Ed25519 envelope as the update manifest,
  `verify_signed_envelope`) can raise the pins without an app release; rollback is blocked by
  `catalogue_version`. Regenerate the JSON with `scripts/build_glm_ocr_catalogue.py`, never by
  hand.
- **Manager.** `glm_ocr_manager.py`: download (per file: upstream, then mirror; separate
  partial file per source), selective runtime extraction (only `sha256_files`, symlinks written
  as regular files), self-test on the staged files, completion marker written LAST, partial
  updates, GPU (Vulkan) runtime, verify, remove (marker first). Status reads the marker only:
  it never hashes and never touches the network.
- **Server.** `engines/glm_ocr_server.py` manages the `llama-server` lifecycle: exact command
  line (`--offline`, loopback, per-session `--api-key`), full runtime re-hash before every
  launch, Windows Job Object / Linux parent-death signal / PID-file reaping, health wait, idle
  shutdown, crash restart, GPU→CPU and Metal→`-ngl 0` fallbacks, memory coordination with the
  Docling worker, warm-timed self-test.
- **Engine.** `engines/glm_ocr_engine.py` is the GLM-OCR conversion: PDF pages (pdfium lock
  held per page) and images (EXIF transpose, transparency flattened, multi-frame TIFF), context
  budget, repetition guard, per-page progress and cancel through `options.job`.
- **Bundled files.** `app/core/assets/` holds the self-test image and the GLM-OCR and llama.cpp
  licence texts.

The API side (`/engines/{name}/…`, `/convert/estimate`) is in [server.md](server.md).

## Lessons

### Tests must not read the real catalogue or the installed engines
- **When:** you write a test for add-on or engine state.
- **Lesson:** a test that reads the real `app/core/addons.json` or the real engine folder
  changes its result when the catalogue is published or when the developer has the add-on
  installed. It failed CI on the release's own commit. Build the catalogue and a temporary pack
  inside the test.
- **Evidence:** a7e8178.
